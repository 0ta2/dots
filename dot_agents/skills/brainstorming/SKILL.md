# Brainstorming

曖昧な要望を、ユーザーが承認できる設計と spec にする。設計が固まるまで実装には進まない。

## 手順

1. 対象リポジトリの既存コード、文書、関連する決定を読んで現状を把握する。
2. 最初に「何を解決したいか (Why)」を確認する。対象リポジトリの
   `CLAUDE.md` / `AGENTS.md` に設計相談のルールがあれば優先する。
3. 目的、制約、成功条件を一問一答で確認する。一度に複数の質問をしない。
4. 複数の独立したサブシステムを含むなら、先に分割と実装順を合意する。
5. 2〜3 案を trade-off 付きで示す。推奨案を先に置き、推奨理由を述べる。
6. 各案から不要な機能を落とし、現在の目的に必要な最小範囲にする (YAGNI)。
7. 方針が定まったら、規模に応じた長さで設計を提示する。必要に応じて構成要素、
   インターフェース、データフロー、エラー処理、テスト方針を含める。
8. ユーザーの承認を得て、設計を
   `~/ghq/github.com/0ta2/harness/docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` に
   書く。他リポで作業中でも必ずこの絶対パスに書く (相対パスだと gitignore が効かない)。
   spec はコミットしない。
9. spec を自分で読み直し、プレースホルダ、矛盾、曖昧さ、過大なスコープを直す。
10. ユーザーに書いた spec のレビューを依頼する。指摘を反映したら自己レビューをやり直す。
11. 承認後、`writing-plans` で実装計画を作る。

## spec の自己レビュー

- `TBD`、`TODO`、未完の節、仮置きの値が残っていないか
- 同じ概念の名称、型、責務が節ごとに食い違っていないか
- 要件を複数の意味に解釈できないか
- 1 つの実装計画として独立して完了できる範囲か
- 目的に不要な機能や将来用の拡張を含めていないか
