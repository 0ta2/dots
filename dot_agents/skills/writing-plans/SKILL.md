# Writing Plans

承認済みの spec を、別の実装者でも順番に実行できる計画へ変換する。

## 1. ファイル構成を決める

タスクを書く前に、作成・変更・テストするファイルと各ファイルの責務を決める。

- 既存コードでは現在の構成と命名に従う
- 1 ファイルに複数の責務を集めない
- ファイル間のインターフェースを、関数名・型・入出力まで具体化する
- 後続タスクが使う名前と型を先に固定する

計画の冒頭には、全タスクに共通する制約 (バージョン下限、命名規則、禁止する操作、
対象リポジトリの範囲) を spec から値のまま書き写す。各タスクの要件はこれを含む。

## 2. タスクに分ける

各タスクを、単独で実装・テスト・commit できる成果物にする。
セットアップ、設定、文書は、それを必要とする成果物のタスクに含める。
独立して合否を判定できない作業を別タスクに分けない。

各タスクに次を記載する。

- 作成・変更・テストする正確なファイルパス
- 前タスクから受け取るものと後続タスクへ渡すもの
- 実装する具体的なコードまたは設定
- 実行するテストコマンドと期待結果
- そのタスクだけを含む commit

## 3. 1 ステップ 1 動作で書く

1 ステップには 1 つの操作だけを書く。例:

1. 失敗するテストを書く
2. テストを実行し、想定した理由で失敗することを確認する
3. 最小の実装を書く
4. 対象テストを実行して通ることを確認する
5. 関連テストを実行する
6. 対象ファイルだけを commit する

## プレースホルダを使わない

`TBD`、`TODO`、「適宜対応」、「適切なエラー処理」、「Task N と同様」を書かない。
必要なコード、値、コマンド、期待結果をその場に記載する。
後のタスクで使う型・関数・設定は、定義するタスクに実物を書く。

## 保存と自己レビュー

計画は `~/ghq/github.com/0ta2/harness/docs/superpowers/plans/YYYY-MM-DD-<topic>.md` に書き、
コミットしない。他リポで作業中でも必ずこの絶対パスに書く (相対パスだと gitignore が効かない)。

書いた後に spec と突き合わせ、次を直す。

- spec の全要件に実装タスクがあるか
- ファイル構成とタスク境界が一致しているか
- タスク間で型、関数名、設定名が一致しているか
- 未定義の前提、プレースホルダ、曖昧な手順がないか
- 依存順に並び、各タスクが独立してテストできるか

自己レビューを終えたら、ユーザーに計画のレビューを依頼する。
