# deep-research

固定予算で Web リサーチを行い、出典付きレポートを**必ず**納品する。
設計の核は「ハードキャップ」と「部分結果でも納品」。

## ハードキャップ (実行中の裁量で増やしてはいけない)

| 項目 | light (デフォルト) | deep / event |
| --- | --- | --- |
| 探索エージェント (初回ラウンド) | 8体 | 20体 |
| 追加ラウンド | なし | 最大1回 (最大8体) |
| サブエージェントのモデル | Claude: haiku / Codex: `gpt-5.6-luna` (`max`) | Claude: sonnet / Codex: `gpt-5.6-luna` (`max`) |
| 1体あたり検索 / ページ取得 | 最大 6 / 8 | 最大 6 / 8 |

「もう1ラウンドあれば良くなる」と感じてもキャップ内で統合する。
不足はレポートの「未調査の穴」節に書くことで対処する。

## 手順

### 1. 引数解析

`/deep-research [--light|--deep|--event] [--unattended] [--no-notify] <質問>`。フラグ無しは light。
質問が無ければユーザーに質問文を求めて終了する。

`--event` は「会社の価値が一気に動くイベント → 波及分析」専用モード。
キャップは deep と同じ。サブクエリ分解と章立ては `templates/event-analysis.md` に**必ず**従う
(5方向固定・否定材料必須・投資助言にしない)。

`--unattended` は無人実行 (Scheduled Task / cron 等) 用。スキルの全手順で
ユーザー入力を求めず最後まで走る。深さのフラグと併用する (例: `--event --unattended`)。
`--no-notify` は `--unattended` と併用し、Discord 通知を抑止する。呼び出し元が
別の配送先を持つ場合にだけ使う。

### 2. スコープ明確化 (最大1回)

質問が曖昧な場合のみ、利用中ツールの入力要求機能で 1 回確認する (期間・対象範囲・用途など)。
具体的な質問ならスキップして即進む。2 回目の確認はしない。
`--unattended` 時はこの手順自体をスキップし、曖昧さは自分で最も自然な解釈に倒して
レポートの冒頭に解釈を明記する。

### 3. 分解と計画提示

調査に必要なサブクエリと担当を、初回ラウンドの上限内で組む。狭い質問で水増しせず、
余った探索枠は使わない。

- light: 8件の独立したサブクエリを作り、各1体を割り当てる (1体なので担当観点は分けない。
  手順4のテンプレートから担当観点の行を省く)
- deep: 10件の主要サブクエリを作り、各2体を独立に割り当てる。一方は一次情報と事実確認、もう一方は別ソース・反証・実務的含意を担当する
- event: `templates/event-analysis.md` の5方向それぞれに4体を割り当てる。各方向で一次情報、定量・時系列、関係者・波及、否定材料を分担する

以下を 1 メッセージで表示し、**承認を待たずに** 4 へ進む
(止めたければユーザーが interrupt する):

- サブクエリ一覧
- 深さ・初回エージェント数・コスト目安 (Claude: light ~$1.3 / deep・event 初回 ~$6-8、追加を上限まで使う場合 ~$8.5-11.5。Codex: Luna max の利用枠消費は実行時の表示に従う)
- deep / event の場合のみ、追加ラウンドの上限 (最大 8 体)

### 4. 並列探索

利用中ツールの並列エージェント機能を、初回ラウンドの全担当分だけ**1回の操作で並列起動**する。
ツールの同時起動上限で受け付けられない場合のみ、上限内の複数バッチに分けて起動する。
Claude Code はキャップ表のモデルを使う。Codex は各起動で `model: gpt-5.6-luna` と
`reasoning_effort: max` を明示指定する。起動 API がこの組み合わせを受け付けない環境では、
既定値や別モデルへ黙ってフォールバックせず、探索前に中断して理由を報告する。各エージェントへの
プロンプトはこのテンプレートを使う:

```
次のサブクエリを Web リサーチする: {サブクエリ}
(全体の調査テーマ: {元の質問})
(あなたの担当観点: {担当観点} — 他の担当は別観点を調べているため、この観点に絞る)

制約:
- Web検索は最大6回、ページ取得は最大8回。超えそうならそこで打ち切って手持ちで回答する
- 一次情報 (公式ドキュメント・原典) を優先する
- 同じサブクエリの他担当が取得しそうなページを繰り返し取らず、担当観点に固有のソースを優先する
- 実装やファイル編集はしない。調査のみ

返答フォーマット:
## 発見事項 (重要度順の箇条書き。各項目に出典 URL を付ける)
## 信頼度と注意点 (情報の鮮度・食い違い・裏取りできなかった点)
## 出典一覧 (URL とタイトル)
```

失敗したエージェントはリトライ 1 回まで。それでも欠けたら欠けたまま先へ進む。
全エージェントが落ちて成果ゼロになった場合は、メインが自分で調査して代替しない。
失敗として報告し、そこで終了する。

### 5. ギャップ確認 (deep / event のみ)

全結果を見て、元の質問に答えるうえで欠けている論点が**明確に**あれば、
追加エージェント最大 8 体を 1 回だけ起動する (テンプレートは同じ)。
light では実施しない。迷ったら実施しない。初回結果を繰り返すだけになるなら実施しない。

### 6. 統合レポート

メインセッションが harness リポジトリの `output/deep-research/YYYYMMDD-{テーマ短縮名}.md` に書く
(`output/` は gitignore 済み)。
結論先行 (`CLAUDE.md` の「記録先」):

```
# {質問}
## 結論 (質問への直接の答え。3-8 行)
## 根拠 (論点ごとに整理。本文中に出典 URL を付ける)
## 未調査の穴 (失敗エージェントの担当分・キャップで踏み込めなかった論点。無ければ「なし」)
## 出典一覧
```

エージェントの生出力を貼り合わせない。矛盾する情報は両論併記して信頼度を添える。

続けて **HTML 版を必ず生成する**: `templates/report_template.html` の `{{PLACEHOLDER}}` を
md の内容で置換し、同じディレクトリに `YYYYMMDD-{テーマ短縮名}.html` を書く。
md が正本、HTML は配布用。テンプレートの章立て (エグゼクティブサマリー / 根拠 /
反証・リスク / 未調査の穴 / 出典) を欠かさない。独自レイアウトを発明しない。

### 7. 配送 (常にHeptabaseジャーナル)

確認は挟まない。対話実行・無人実行を問わず、手順 6 で書いた md 全文を当日の
Heptabase ジャーナルへ追記する (要約ではなく全文。`output/` 配下のローカルファイルは
ユーザーが実際には見に行かないため、必ず Heptabase 側に実体を持たせる):

```bash
heptabase journal append <YYYY-MM-DD> --content-file output/deep-research/<書いたファイル名>.md
heptabase journal append <YYYY-MM-DD> --content "(HTML版: output/deep-research/<書いたファイル名>.html)"
```

Heptabase カードは作らない (ジャーナルが正本。価値がある調査はユーザーが後日カード化する)。

続けて:

- **対話実行**: ジャーナルに追記した日付をユーザーに伝えて終える
- **`--unattended`**: `--no-notify` が無ければ `bash scripts/discord-notify.sh --to assistant` で
  結論 1〜3 行とジャーナル日付を通知する。`--no-notify` 指定時はジャーナル追記した時点で終える
- **--event の場合**: さらに kabu-lab への仮想記録 (event-analysis.md 参照) を行う

(起動元が Scheduled Task かどうかを推測しない。フラグの有無だけで判定する)

## エラー方針

- Web検索が使えない環境なら、探索を始める前に中断して報告する
- どれだけ結果が欠けても手順 6-7 は必ず実行する。ゼロ納品はこのスキルの禁止事項
